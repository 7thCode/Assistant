01概要と経緯

GGUF は、GGML(および GGML ベースの実行系)でモデルを推論するためのバイナリ形式です。高速に読み書きでき、人間が構造を追いやすいことを目的に設計されています。PyTorch などで作られたモデルを GGUF に変換して使うのが一般的な流れです。llama.cpp・node-llama-cpp・Ollama・LM Studio などが読み込めます。

Assistant では、チャットに使うモデルだけでなく、LoRA アダプタや RAG 用の埋め込みモデルも GGUF 形式です。初回に自動ダウンロードされる既定モデルも GGUF で、2分割されています。

設計目標

  • 単一ファイルで配布できる: 外部ファイルを必要としません。
  • 拡張できる: 既存のモデルとの互換性を壊さずに、新しい情報を追加できます。
  • mmap に対応: ファイルをメモリに直接対応付けて、高速に読み込めます。
  • 実装が簡単: 言語を問わず、少ないコードで、外部ライブラリなしに読み書きできます。
  • 情報が完全: モデルの読み込みに必要な情報が全て入っており、利用者が追加情報を渡す必要がありません。

前身の形式との違い

形式バージョン特徴
GGMLなし基本形式。バージョンもアライメントもありません。
GGMFあり(1種類のみ)GGML にバージョンを加えたものです。
GGJTv1 〜 v3テンソルをアライメントして mmap に対応。v1〜v3 は構造が同じで、v3 は量子化方式が以前のものと非互換です。llama.cpp のモデルに使われていました。
GGUFv1 〜 v3ハイパーパラメータを型付きのキー・バリュー(メタデータ)に変更。アーキテクチャを明示でき、項目の追加が互換性を壊しません。

前身の形式は、ハイパーパラメータが「型のない値の並び」だったため、(1) どのアーキテクチャのモデルか識別できない、(2) 項目を足すと既存モデルとの互換性が壊れる、(3) アーキテクチャごとに変換スクリプトが必要、といった問題がありました。GGUF の最大の違いは、これらをキー・バリュー構造のメタデータで解決した点です。

GGUF 自身のバージョン

版変更点
v1初版。
v2長さなどの数量を表す値を uint32 から uint64 に変更し、より大きなモデルに対応しました。
v3ビッグエンディアンに対応しました(現行)。

バージョン番号は「ファイル構造そのもの」が変わる時だけ上げます。構造に影響しない変更(新しいキーの追加など)は、メタデータで表現します。

02全体レイアウト

GGUF ファイルは、次の5つの領域が先頭から順に並んだ構造です。各領域名の下の大きさは、Assistant の既定モデル(2分割のうち1つ目)を実際に測った値です。

① ヘッダ
24 バイト
マジックナンバー GGUF、バージョン、テンソル数、メタデータ数。
② メタデータ
5,934,187 バイト
キー・バリューが29個。そのうちトークナイザ関連の4項目だけで 5,933,173 バイト(99.98%)を占めます。
③ テンソル情報
15,931 バイト
280個のテンソルの名前・形状・型・オフセット。1個あたり約57バイトです。
④ パディング
2 バイト
0x00 で埋めて、テンソルデータの開始位置を ALIGNMENT(この例では32)の倍数に揃えます。
⑤ テンソルデータ
3,987,251,200 バイト
重み本体。ファイルの 99.85% を占めます。

24 + 5,934,187 + 15,931 + 2 + 3,987,251,200 = 3,993,201,344 バイト(実ファイルサイズと一致)。テンソルデータの開始位置は 5,950,144 = 32 × 185,942 です。

共通ルール

  • フィールドは、特に指定がない限り、アライメントなしで順番に詰めて書かれます。
  • 文字列は「長さ(uint64)+ UTF-8 のバイト列」で、NUL 終端はありません。
  • ALIGNMENT はメタデータ general.alignment で指定します(8の倍数)。未指定なら 32 です。この実例には general.alignment がなく、32 が使われています。
  • テンソルデータの開始位置は、テンソル情報の終端を ALIGNMENT の倍数に切り上げた位置です。間は 0x00 で埋めます。
  • 各テンソルの offset はテンソルデータ領域の先頭からの相対位置(ファイル先頭ではありません)で、ALIGNMENT の倍数でなければなりません。
  • 既定はリトルエンディアンです。ビッグエンディアン版では、メタデータの値もテンソルも全てビッグエンディアンになります。ただし仕様上、ファイルからエンディアンを判別する方法はありません。

04メタデータ(キー・バリュー)

ヘッダの直後に、キー・バリューが metadata_kv_count 個並びます。モデルの構造(層数・次元数など)、トークナイザ、チャットテンプレート、出所などが、全てここに入ります。

キー・バリューの符号化

1件は「キー(文字列)→ 値の型(uint32)→ 値」の順です。次は、実ファイルの最初の1件(general.architecture = "qwen2"、45 バイト)です。

00000018  14 00 00 00 00 00 00 00  67 65 6e 65 72 61 6c 2e
00000028  61 72 63 68 69 74 65 63  74 75 72 65 08 00 00 00
00000038  05 00 00 00 00 00 00 00  71 77 65 6e 32
キー長 = 20(uint64) キー = "general.architecture" 値の型 = 8(STRING) 文字列長 = 5(uint64) 値 = "qwen2"
  • キーは ASCII の階層キーで、各階層は lower_snake_case、区切りは . です。最大 65,535 バイトです。
  • コミュニティ独自のキーは、衝突を避けるためにコミュニティ名を接頭辞にします(例: rustformers.)。広く使われるようになったキーは、標準キーに昇格することがあります。
  • 存在しないキーは「不明」として扱い、リーダーが既定値を使うかエラーにするかを決めます。

LoRA アダプタと mmproj

GGUF は、モデル本体以外にも使われます。general.type で種類を区別します。

  • LoRA アダプタ(general.type = "adapter"): llama.cpp の変換スクリプトは、Hugging Face PEFT の LoRA を GGUF にする際、adapter.type = "lora" と adapter.lora.alpha(float32)を書き込みます。テンソルは元のテンソル名に .lora_a / .lora_b が付いた名前になります(例: blk.0.attn_q.weight.lora_a)。Assistant の LoRA 機能が読み込むのはこの形式です。
  • mmproj: 画像などのマルチモーダル入力用のプロジェクタです。本体とは別ファイルで、ファイル名の先頭に mmproj- が付きます。

仕様書では、LoRA と プロンプト形式のメタデータは「TODO」のままです。上の adapter.* は、仕様書ではなく llama.cpp の実装に基づく情報です。

06量子化ブロックの構造

量子化されたテンソルは、行方向(最も内側の次元 ne[0])を固定長のブロックに区切り、ブロックごとに「スケール(と最小値)+ 低ビットの整数」として保存します。ブロックの構造体は ggml のソース(ggml-common.h)で定義されています。

bit/重み = バイト数 × 8 ÷ 要素数。例: Q4_K は 144 × 8 ÷ 256 = 4.5。d・dmin は 16bit 浮動小数点(fp16)です。Q8_K は中間量子化と内積計算用、IQ 系・TQ 系・MXFP4 はまた別のブロック構造を持ちます。

Q4_K の中身

K-quants は、256 要素の「スーパーブロック」を単位とします。Q4_K は、これを 32 要素ずつの 8 つのサブブロックに分け、各要素を x ≈ a × q + b(q は 4bit の整数)で復元します。a(スケール)と b(最小値)はサブブロックごとに 6bit で持ち(8 × 12bit = 96bit = 12 バイト = scales)、その 6bit 値を実数に戻すための係数が、スーパーブロック全体の d と dmin です。2 + 2 + 12 + 128 = 144 バイトです。

Q4_K_M は「Q4_K だけ」ではない

ファイル全体の平均は 4,677,120,000 × 8 ÷ 7,615,616,512 = 4.913 bit/重みで、Q4_K の理論値 4.5 より大きくなっています。理由は、一部のテンソルが Q6_K(6.5625 bit)に引き上げられているためです。general.file_type の「MOSTLY」は、この意味です。

  • llama.cpp の量子化ツール(llama-quantize)が、この配分を決めています。ソース(llama-quant.cpp)には「先頭 1/8・末尾 1/8・その間は 3 層おき」の層を高精度にする use_more_bits という規則があり、選び方の細部は llama.cpp のバージョンによって変わります。
  • 出力層(output.weight)と attn_v・ffn_down を重点的に守るのは、量子化による劣化がモデルの品質に影響しやすいテンソルだからです。同じ理由で、Q3_K_M や Q2_K も、名前の理論値(3.4375 / 2.625 bit)より大きい bit/重みになります(モデルガイドの表)。

次元の制約とフォールバック

ブロックは行方向に並ぶため、ne[0] がブロックの要素数(K-quants なら 256)の倍数でないテンソルは、その型で量子化できません。llama.cpp の量子化ツールは、その場合、別の型に切り替えます(tensor_type_fallback)。この実例では、3584 = 14 × 256、18944 = 74 × 256、512 = 2 × 256 と、量子化された全テンソルの ne[0] が 256 の倍数なので、フォールバックは起きていません。

07分割ファイル

大きなモデルは、複数のファイルに分割して配布されます。ファイル名の末尾は -00001-of-00002.gguf の形で、1 から始まる 5 桁のゼロ埋めです。Assistant の既定モデルは、まさにこの形の2分割です。

項目1つ目(…-00001-of-00002.gguf)2つ目(…-00002-of-00002.gguf)
ファイルサイズ3,993,201,344 バイト689,872,288 バイト
テンソル数28059
メタデータ数29(全て)3(split.* のみ)
テンソルデータの開始位置5,950,1443,488
含まれるテンソルtoken_embd.weight、output.weight、ブロック 0〜22 の全て、ブロック 23 の一部ブロック 23 の残り、ブロック 24〜27、output_norm.weight
  • 各ファイルは、それ自体が完全な GGUF ファイルです。それぞれが独自のヘッダ、テンソル情報、アライメントを持ち、offset は各ファイル自身のテンソルデータ領域が基準です。
  • 分割の情報は split.no(そのファイルの番号)・split.count(総数)・split.tensors.count(全ファイル合計のテンソル数)で表します。実例では 280 + 59 = 339 で split.tensors.count と一致します。これらは llama.cpp の llama-gguf-split が書き込むキーです。
  • split.no は 0 始まりで、ファイル名の番号(1 始まり)とは1つずれます(2つ目は split.no = 1)。
  • アーキテクチャやトークナイザなどのメタデータは、1つ目のファイルだけが持ちます。2つ目には split.* の3つしかありません。
  • 分割の境界は層ではなくテンソルの数で決まります。実例では、ブロック 23 のテンソルが2つのファイルにまたがっています。
  • llama.cpp では、最初のファイルを指定すれば、残りは自動的に読み込まれます。分割・結合には llama-gguf-split を使います。

09読み込み手順とツール

読み込みの手順

  1. 先頭 4 バイトが GGUF であることを確認し、version、tensor_count、metadata_kv_count を読みます。
  2. メタデータを metadata_kv_count 回、「キー → 値の型 → 値」の順に読みます。
  3. テンソル情報を tensor_count 回、「名前 → 次元数 → 各次元 → 型 → offset」の順に読みます。
  4. ここまでの終端を ALIGNMENT(general.alignment、なければ 32)の倍数に切り上げると、テンソルデータの開始位置です。
  5. テンソル i の位置は「開始位置 + offset」、サイズは「要素数 ÷ ブロックの要素数 × ブロックのバイト数」です(型ごとに決まります)。mmap していれば、その位置を指すだけで使えます。

Python での最小実装

次のコードは、ヘッダ・メタデータ・テンソル情報を読み、テンソルデータの開始位置を返します。この実例の1つ目のファイルで実行し、version = 3、メタデータ 29 個、テンソル 280 個、開始位置 5,950,144 が得られることを確認したコードです。このコードはリトルエンディアン(既定)専用で、struct のフォーマットを全て < に固定しています。ビッグエンディアンのファイルでは、全ての値(メタデータの値・テンソルを含む)がビッグエンディアンになるため、> に切り替える必要があります。ただし、仕様上、ファイルからエンディアンを判別する方法はないため、利用者や実装側が指定します。

import struct

# リトルエンディアン専用("<")。ビッグエンディアン版のファイルには ">" が必要

def read_gguf(path):
    f = open(path, "rb")
    u = lambda fmt: struct.unpack(fmt, f.read(struct.calcsize(fmt)))[0]
    s = lambda: f.read(u("<Q")).decode("utf-8")            # 長さ(u64) + UTF-8

    assert f.read(4) == b"GGUF"
    version, n_tensors, n_kv = u("<I"), u("<Q"), u("<Q")

    SCALAR = {0: "<B", 1: "<b", 2: "<H", 3: "<h", 4: "<I", 5: "<i",
              6: "<f", 7: "<?", 10: "<Q", 11: "<q", 12: "<d"}

    def value(t):
        if t == 8:                                          # string
            return s()
        if t == 9:                                          # array: 要素型 + 要素数 + 要素
            et, n = u("<I"), u("<Q")
            return [value(et) for _ in range(n)]
        return u(SCALAR[t])

    meta = {}
    for _ in range(n_kv):
        key = s()
        meta[key] = value(u("<I"))

    tensors = []
    for _ in range(n_tensors):
        name = s()
        dims = [u("<Q") for _ in range(u("<I"))]
        ggml_type, offset = u("<I"), u("<Q")
        tensors.append((name, dims, ggml_type, offset))

    align = meta.get("general.alignment", 32)
    data_start = (f.tell() + align - 1) // align * align    # 次の ALIGNMENT 境界へ
    return version, meta, tensors, data_start

トークナイザの配列は数十万要素あり、実例のヘッダ部(テンソルデータより前)は約 5.95MB で、その 99.7% がトークナイザですです。語彙が不要な場合は、配列を読み飛ばす実装にすると速くなります。

実装上の注意

  • 長さと個数は uint64 です(v2 以降)。文字列の長さも uint64 です。
  • 値の型 BOOL は 0 か 1 のみが有効です。それ以外は不正なファイルとして扱います。
  • 各テンソルの型ごとのブロック構造(要素数とバイト数)は、ggml-common.h に依存します。新しい型が追加されることがあるため、未知の型では読み飛ばすかエラーにします。
  • 書き込む側は、各テンソルの offset を ALIGNMENT の倍数にし、間を 0x00 で埋めます。
